# กระแสข้อมูล: จากใบเสร็จสู่ bINT

## 1.3 กระแสข้อมูล: จากใบเสร็จสู่ bINT

การเดินทางของใบเสร็จประกอบด้วยสองเฟส

**เฟส A — ซิงโครนัส (ผู้ใช้กำลังรอ):**

1. ไคลเอนต์ส่งไฟล์ไปยัง upload endpoint เซิร์ฟเวอร์บีบอัดภาพ ลบเมทาดาทา EXIF และเก็บผลลัพธ์ลงในที่เก็บอ็อบเจกต์ ดัชนีการลบข้อมูลซ้ำแบบ perceptual-hash ถูกตรวจสอบก่อนการวิเคราะห์
2. สำหรับอินพุตที่เป็นภาพ vision LLM (02 ขั้นตอน 2) อ่านใบเสร็จจากภาพโดยตรงในการเรียกครั้งเดียว สำหรับอินพุตที่เป็น PDF ชั้น OCR (02 ขั้นตอน 1) จะแยกข้อความก่อน แล้วป้อนเข้าสู่ขั้นตอน LLM เดียวกัน
3. LLM คืนค่าเป็น **ข้อความธรรมดาแบบติดป้ายกำกับ**: บล็อกของบรรทัด `FIELD: value` สำหรับผู้ค้า วันที่ ยอดรวม และช่องทางการชำระเงิน พร้อมตารางคั่นด้วย pipe สำหรับรายการสินค้า การ parse เป็นแบบตั้งรับ — บรรทัดที่หายไปหรือผิดรูปแบบจะทำให้ช่องนั้นเป็น `null` และท่อยังคงทำงานต่อ
4. ชั้น regex/กฎ (02 ขั้นตอน 3) ปรับยอดรวมให้ตรงกันและตรวจสอบวันที่
5. merchant resolver (02 ขั้นตอน 5) แนบเอกลักษณ์ผู้ค้า
6. ชั้นความน่าเชื่อถือ (03) จำแนกคุณภาพของใบเสร็จ และรางวัลถูกคำนวณภายในคำขอเดียวกัน ผู้ใช้จึงเห็นตัวอย่างที่ตรวจสอบแล้วพร้อมกับรางวัล

**เฟส B — อะซิงโครนัส (การชำระเงินเบื้องหลัง):**

7. post-process worker เบื้องหลังแก้ไขแต่ละรายการสินค้าเป็น canonical product ID (02 ขั้นตอน 4) โดยใช้การจับคู่แบบ fuzzy ฝั่งฐานข้อมูลพร้อม LLM สำรอง และรวมผลการจำแนกคุณภาพของใบเสร็จเข้ากับคะแนนความน่าเชื่อถือสะสมของผู้ใช้
8. settlement worker รวมเครดิต bINT ที่เข้าเกณฑ์ ใช้เพดานรายวัน และสร้างรากการแจกจ่ายของ epoch สำหรับสิทธิ์เคลม INT ที่เกี่ยวข้อง
9. รากการแจกจ่ายถูกผูกไว้บนเชน indexer ยืนยันการโอน INT ที่เคลมจากผู้แจกจ่ายกลับไปยังบัญชีแยกประเภทนอกเชน

ผู้ใช้เห็นเฟส A ภายในไม่กี่วินาที เฟส B สิ้นสุดแบบอะซิงโครนัส บัญชีแยกประเภท bINT นอกเชนยังคงเป็นที่มาของความจริงสำหรับเครดิตการมีส่วนร่วม ส่วนรากบนเชนและการโอนเมื่อเคลมจะบันทึกการแจกจ่าย INT ที่เกี่ยวข้อง
