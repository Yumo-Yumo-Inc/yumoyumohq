## 5.3 Запись чека (нормативная)

Значения достоверности и оценка доверия показаны как заполнители. Производственные диапазоны, границы полос и веса сигналов управляются во внутреннем операционном слое.

### Соглашения о полях

| Соглашение | Правило |
|---|---|
| ID | UUID в качестве первичных ключей для чеков и торговцев; серийные целочисленные id в таблицах событий и реестра. |
| Суммы в валюте | Десятичные значения, сериализуемые как канонические десятичные строки (2 знака после запятой для денег). |
| Метки времени | ISO 8601 с суффиксом `Z`. Всегда UTC. |
| Хэши | Шестнадцатеричные символы в нижнем регистре, алгоритм именуется контекстом поля. |
| Nullable | Отсутствующие поля используют явный `null`. |
| Перечисление статусов | `verified`, `saved`, `analyzed`. |

### Статусы и обработка доказательства оплаты

Действующие значения статуса:

```
analyzed  — выход конвейера получен, запись ещё не сохранена как удержанная
saved     — сохранена пользователем
verified  — прошла ворота верификации; пригодна для вознаграждений и агрегированного слоя
```

Документы с ограниченным доказательством оплаты (например, страница заказа) обрабатываются **отдельной парой полей**, а не значением статуса: `proof_status` помечает запись как ожидающую доказательства оплаты, а `linked_receipt_id` указывает на документ-доказательство, который её разрешает, когда пользователь его загружает. Такие записи учитываются в собственной статистике пользователя, но не приносят вознаграждения и не попадают в анонимизированный агрегат.

Поток ручной проверки для пограничных случаев запланирован; он не входит в действующий набор статусов.

Чек `verified` зарабатывает bINT. Агрегированная обработка неверифицированных записей следует правилам 5.8.
